# Bug/Issue Agent Testing and Debugging Runbook

## Purpose

The Bug/Issue Agent verifies work completed by the Backend Agent and UI Agent before GitHub checklist items are marked as complete.

The Bug/Issue Agent must never approve a task without checking the available implementation and test evidence.

## Verification Workflow

1. Read the current GitHub issue requirements.
2. Review the implementation produced by the Backend Agent or UI Agent.
3. Inspect the files created or modified by the implementation agent.
4. Review available test results and runtime evidence.
5. Compare the completed work with the exact GitHub issue requirements.
6. Detect missing functionality, errors, failed tests, or integration problems.
7. Return failed work to the appropriate agent for correction.
8. Verify the corrected implementation again.
9. Mark checklist items eligible for completion only after successful verification.

## Backend Testing

For backend tasks:

- Check that required backend files exist.
- Compile the Python source code.
- Run pytest tests.
- Review test output and errors.
- Check required API implementation.
- Check validation and error handling when required.
- Verify that the implementation matches the GitHub issue requirements.

Backend tests are executed through:

`orchestrator/test_runner.py`

## UI Testing

For frontend tasks:

- Check that required frontend files exist.
- Review the generated HTML, CSS, and JavaScript.
- Compare the implementation with the Google Stitch source design when required.
- Check forms, buttons, input fields, loading states, and error states required by the issue.
- Check frontend/backend API integration when required.
- Verify that the implementation matches the GitHub issue requirements.

The original Google Stitch evidence is stored in:

`frontend/stitch-design.html`

## PASS Behavior

A task receives PASS only when all requirements for the current verification are supported by implementation or test evidence.

Expected final status:

`VERIFICATION: PASS`

Only verified GitHub checklist items may then be changed from `[ ]` to `[x]`.

## FAIL Behavior

A task receives FAIL when required functionality is missing, tests fail, implementation evidence is insufficient, or the work does not satisfy the GitHub issue.

Expected final status:

`VERIFICATION: FAIL`

When verification fails:

- GitHub checklist items remain unchecked.
- Backend failures are returned to the Backend Agent.
- UI failures are returned to the UI Agent.
- The corrected work must be verified again.

## Debugging Failed Backend Work

1. Read the Bug/Issue Agent failure report.
2. Identify the failed requirement.
3. Send the failure information to the Backend Agent.
4. Apply the corrected backend files.
5. Run backend tests again.
6. Send the new implementation and test evidence to the Bug/Issue Agent.

## Debugging Failed UI Work

1. Read the Bug/Issue Agent failure report.
2. Identify the failed UI requirement.
3. Send the failure information to the UI Agent.
4. Apply the corrected frontend files.
5. Preserve `frontend/stitch-design.html` as the original Stitch evidence.
6. Send the corrected UI back to the Bug/Issue Agent for verification.

## Running the Workflow

From the project root with the virtual environment activated, run:

`python -m orchestrator.workflow`

The workflow selects the next incomplete GitHub issue, routes the work, verifies the result, and updates verified checklist items only after successful verification.

## Safety Rules

- Never expose API keys or GitHub tokens.
- Never store secrets in source code.
- Never execute arbitrary shell commands generated by an AI agent.
- Never mark failed or unverified requirements as complete.
- GitHub writes must use the project's controlled approval workflow.
